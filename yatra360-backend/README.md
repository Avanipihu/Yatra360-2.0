# Yatra360 Backend (Inside User Page)

FastAPI + SQLAlchemy backend for the tourist dashboard. Field names in
every JSON response are camelCase on purpose, matching the shapes already
used in `src/data/mockData.js` on the frontend — so swapping the frontend
from mock data to this API is a drop-in change, not a rewrite.

## Running it

```bash
python3 -m venv venv
source venv/bin/activate        # venv\Scripts\activate on Windows
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload --port 8000
```

Runs on `http://localhost:8000`. Interactive docs at
`http://localhost:8000/docs` (Swagger UI, auto-generated by FastAPI).

On first startup, tables are created and sample data (matching the
frontend's `mockData.js`) is seeded automatically — no manual seeding step.

### Switching to real PostgreSQL

Edit `.env`:
```
DATABASE_URL=postgresql+psycopg2://yatra360_user:password@localhost:5432/yatra360
```
Uncomment `psycopg2-binary` in `requirements.txt` and reinstall. Nothing
else in the code needs to change — SQLAlchemy handles both.

## API reference

| Method | Path | Owner | Notes |
|---|---|---|---|
| GET | `/api/places` | Person 1 | Optional `?category=` and `?group_type=` filters |
| GET | `/api/places/{id}` | Person 1 | |
| GET | `/api/hotels?budget=` | Person 1 | Falls back to full list if budget has no match |
| POST | `/api/itinerary/generate` | Person 1 | Body = `TripProfileIn`; saves a `Trip` + `ItineraryStop` rows, returns the generated plan |
| GET | `/api/itinerary/{trip_id}` | Person 1 | Re-fetch a saved trip |
| GET | `/api/mobility/routes?to=<placeId>` | Person 2 | Falls back to generic route options if the place has none of its own |
| GET | `/api/safety/emergency-contacts` | Person 3 | |
| GET | `/api/safety/weather?location=` | Person 3 | Mocked — swap for IMD/licensed weather API later |
| POST | `/api/crowd/alternatives` | Person 4 | Body `{ "placeIds": [...] }` → overcrowded→alternative pairs |
| GET | `/api/crowd/alternatives/trip/{trip_id}` | Person 4 | Same, but reads place ids from a saved trip |
| GET/POST | `/api/reports` | Person 5 | City issue reports (pothole, waterlogging, etc.) |
| GET | `/api/parking` | Person 5 | Parking availability by location |
| GET | `/api/health` | — | Health check |

## Project structure

```
app/
  main.py            FastAPI app, CORS, startup seeding
  config.py          Env var loading (DATABASE_URL, CORS_ORIGINS)
  database.py        SQLAlchemy engine/session
  models.py          ORM tables: Place, Hotel, RouteOption,
                      EmergencyContact, ParkingSpot, CityReport,
                      Trip, ItineraryStop, PlaceAlternative
  schemas.py         Pydantic request/response models (camelCase)
  seed_data.py       Sample data mirroring the frontend's mockData.js
  services/
    recommendation.py  Itinerary filtering/generation logic
                        (mirrors TripContext.jsx on the frontend)
  routers/
    places.py, hotels.py, itinerary.py, mobility.py,
    safety.py, crowd.py, reports.py, parking.py
```

## Design notes / guardrails carried over from planning

- `estimated_demand` is intentionally named "estimated," never "real-time
  crowd count" — there's no live crowd-tracking data source in this
  prototype, and the API/UI language should stay honest about that.
- Every `Place`, `EmergencyContact` has a `source` and `last_verified`
  field so the frontend can render its verification badge — don't drop
  these when adding new records.
- `Trip` has no `user_id` yet, since login/auth is a separate team module.
  Once that's ready, add a foreign key to whatever user table it creates
  and pass the current user's id into `/api/itinerary/generate`.
- Hotels are sample data (see each hotel's `source` field) — swap for a
  verified/government/licensed source before treating this as real
  inventory, per the project's data-honesty guardrail.

## Connecting the React frontend

In the frontend project, replace the static imports from `mockData.js`
with `fetch` calls to `http://localhost:8000/api/...` inside a small
`src/api/client.js` wrapper. Because response fields are already
camelCase and match the mock data's shape, most components won't need
any changes beyond swapping the data source.
